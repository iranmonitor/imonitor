# Network regression tests

`bash scripts/test-bpf-packets.sh` builds and runs the production IPv4 rewriting algorithm against packet fixtures. It requires a C compiler and the Linux/libbpf development headers. The fixtures independently verify IPv4, TCP and UDP checksums, UDP zero semantics, exact source/destination/interface/protocol matches, ESP payload preservation, IPv4 options, fragmented TCP headers and malformed input handling.

`IMONITOR_ACCEPT_DISPOSABLE=1 bash tests/source-ip-acceptance.sh /absolute/path/to/iranmonitor_node-tests` runs opt-in Rust acceptance tests in temporary network namespaces inside a disposable Linux VM. Never run this against a production network namespace. Build the Rust test binary with `cargo test --bins --no-run`; the network acceptance tests are ignored during ordinary runs. Required tools: iproute2, iptables/ip6tables (including restore/save and extension libraries), bpftool, sysctl and standard shell utilities. The VM kernel must support network namespaces, IPv4/IPv6 NAT/conntrack, clsact/flower/HTB/tc NAT and XDP/BPF maps.

Set `IMONITOR_BPF_HELPER` to the compiled helper path, or place it at `/tests/bin/imonitor-bpf`; put the matching object at `/tests/bpf/xdp_ingress.o`. The helper finds this object relative to its executable. Tests cover actual IPv4/IPv6 SNAT and UDP replies, paired IPv4 tc NAT/XDP attach and checksums, owned-rule deletion, preservation of unrelated NAT rules, overlapping traffic counters, forwarding, connection-limit rule installation/clear and shaping reapply/remove. Namespace names include the shell PID, existing namespaces are rejected, and cleanup removes only namespaces created by this run.

Set `IMONITOR_BPF_TEST_BINARY` to the compiled helper Rust test binary to also run the real tc parser round-trip regression. It installs and removes owned filters for protocol numbers 0, 4, 6, 17, 41, 47, 50, 51, 97, 115 and 255, and verifies the installed kernel selector through tc JSON. TCP/UDP use named tokens; all other protocol numbers use explicit hexadecimal because tc flower parses numeric IP protocols in base 16. iptables protocol arguments remain decimal.

Ordinary Rust tests also use command mocks to exercise missing/foreign XDP preflight, failed-apply rollback, deleted interfaces, corrupt ownership state and overlapping paired selectors. Shaping regressions simulate IPv4 filter success followed by IPv6 failure, verify rollback preserves other classes/filters, and retain a dirty applied flag if cleanup fails so deletion can retry. Cleanup refuses an existing root qdisc without matching ownership metadata, including legacy database rows marked applied; it never adopts a tree from the database flag alone. A missing device or already-removed root is treated as cleaned. These failure mocks complement the guest acceptance tests; they do not execute host network commands.

Exact numeric protocol `0` is distinct from `any`: source-IP SNAT and traffic counters use an IPv4/IPv6 `u32` header matcher because iptables reserves `-p 0` for its wildcard. Ports are supported only for TCP/UDP; `any` with a port expands to those two protocols.

AH (`51`) remains valid for traffic monitoring, but explicit AH source-IP rewrites are rejected in both SNAT and paired modes because AH authenticates IP addresses. Legacy wildcard selectors remain readable for compatibility; this does not establish support for rewriting AH traffic. Protocol `51` in the low-level tc parser round-trip only checks numeric selector parsing, not working AH packet forwarding.

## ESP cipher and legacy-state checks

New managed ESP uses AES-256-CBC with HMAC-SHA256 authentication (128-bit tag) and directional HKDF-SHA256 encryption/authentication keys. The runner test `manual_esp_cbc_uses_independent_directional_keys_and_authenticated_command` verifies mirrored peers derive matching keys for each direction, separate keys for encryption/authentication and changed secrets, and construct authenticated CBC XFRM states. Actual ESP packet exchanges, state reuse and monitor/native-speed-test paths are exercised by the separate `scripts/kernel-acceptance.sh` harness described in [protocol-validation.md](../docs/protocol-validation.md).

Saved configurations without a cipher retain their legacy AES-GCM identity. The runner test `saved_esp_gcm_is_identifiable_but_cannot_be_recreated_with_static_keys` checks that unsafe static GCM creation/recreation is rejected. Exact existing live SAs/policies may be reused without resetting replay/sequence state; monitoring/MTU edits preserve them. Changes to an enabled managed legacy check's forwarding identity are rejected before teardown. Disable/delete and coordinated migration to CBC/HMAC with a new random shared secret remain available. Manual ESP does not add automatic rekey or forward secrecy; use WireGuard or externally managed dynamic IKE when automatic session key management is required. See [tunnel-profiles.md](../docs/tunnel-profiles.md) for the deployment policy.

Packet fixtures, command mocks and disposable namespace tests establish only their tested algorithm, commands and guest/kernel behavior. They do not establish a two-host WAN throughput comparison against 1.2.2.
